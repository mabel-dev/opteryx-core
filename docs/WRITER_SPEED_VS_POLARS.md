# rugo writer speed vs polars: where the time goes

Investigation, 2026-10-16, followed the same day by implementation of the fix
proposals in §5. Sections 1–5 describe the code as it was before the changes.
§6 says what was built, what the leave-one-out A/B kept and deleted, and the
resulting numbers.

## Question

The rugo.dev write benchmark (`rugo.dev/benchmarks/measure_writes.py`,
results in `benchmarks/results/2026-10-16-writes.json`) shows rugo losing to
polars in all three text and columnar formats. The table is 200,000 rows x 50
columns (17 INT64, 17 FLOAT64, 16 VARCHAR, from `gen_data.py`'s `wide.csv`). Each
library writes from its own in-memory table at its default threading. Times are
best of 5, in ms:

| format | rugo 0.5.2 | polars | pyarrow | duckdb |
|---|---:|---:|---:|---:|
| Parquet (zstd) | 774 | 24 | 347 | 231 |
| CSV | 220 | 10.5 | 209 | 220 |
| JSONL | 67 | 17 | n/a | 277 |

This report asks whether that gap comes from defaults, from threading, or from
real encoder cost.

## Answer in one paragraph

Two thirds of the gap, measured as a ratio, is threading. polars runs on all 18
cores. rugo's Parquet and CSV writers run on one, and its JSONL writer runs on 8.
On a single thread polars takes 279 ms (Parquet), 106 ms (CSV) and 180 ms (JSONL),
so rugo's real per-core gap is **2.7x, 2.1x and 2.4x**. That gap has two causes:

- **Parquet:** two defaults that polars doesn't pay. Dictionary attempts cost
  about 260 ms, and on this table the dictionaries make the file larger after
  zstd. Bloom filters cost 55–120 ms and add 10 MB to a 48 MB file. With both off,
  rugo takes 358 ms against polars' 279 ms.
- **CSV and JSONL:** float formatting, and nothing else. rugo matches polars on
  int and string columns. Float columns cost 3.3x as much: ryu, followed by a
  scientific-notation reparse.

## Method

- **Build:** the current tree, opteryx-rugo 0.9.167 build 3692, `rugo_native` built
  15:02. I copied `rugo/` and `draken/` (the `.so` and `.py` files) to a scratch
  directory, so a rebuild by another session during the runs could not change the
  library under test (see the SOSWAP memory note). The imports used Python 3.14.5
  with `PYTHONPATH` set to that copy. I compared it with published rugo 0.5.2 in a
  Python 3.13 venv. polars 2.0.0, pyarrow 26.0.0 and duckdb 1.5.6 ran in the 3.14 venv.
- **Data:** generated by `gen_data.py`, byte-identical to the benchmark's.
- **Runs:** every number below is best of 5 inside a fresh process. Each spec ran
  2–3 times, in alternating order with the specs it is compared against (round-robin
  over the spec list, rotated each round). Rounds agreed within about 2%.
- **CPU time:** process `ru_utime + ru_stime` across the write. On a single-threaded
  writer it equals wall time. On a threaded writer it shows total work.
- **Machine:** M-series Mac, 18 cores, quiet before each run. One caveat: another
  session ran the rugo.dev write benchmark at 14:37 UTC, overlapping my first
  rounds. Those rounds matched the later ones (for example, rugo Parquet took
  732–750 ms in every round), so I kept them.
- **Profiles:** `samply record`, 20–80 iterations per writer, symbolised with
  `dsymutil` (built from the `build/temp` `.o` files) and `atos`. Samples whose
  leaf frame is `libsystem_kernel` (waits) are dropped. "Self" means the leaf
  frame; "incl." means the function is anywhere on the stack.

|---|---:|---:|

## 2. Parquet defaults

These runs use the full table, the tree build, a single thread (rugo's Parquet
writer has no threads) and best of 5:

| rugo `write_parquet(...)` | ms | file MB |
|---|---:|---:|
| defaults (`zstd`, bloom on, dictionary on) | 740 | 48.2 |
| `bloom_filters=False` | 685 | 38.4 |
| `dictionary=False` | 481 | 43.4 |
| `bloom_filters=False, dictionary=False` | **358** | **33.6** |
| `page_index=False` | 742 | 48.2 |
| `row_groups_per_block=1` | 741 | 48.2 |
| `max_rows_per_row_group=0` (one row group) | 607 | 39.0 |
| `compression="none"` | 557 | 101.3 |
| `compression="none"`, bloom off, dictionary off | 133 | 98.3 |
| *polars, 1 thread (zstd level 3, statistics on)* | *279* | *36.3* |
| *polars, 1 thread, uncompressed* | *88* | *91.0* |

- **`page_index` costs nothing at the defaults.** It only takes effect when
  `max_page_bytes > 0`, and the default is 0. The column-major block layout costs
  nothing either.
- **Dictionary attempts are the biggest default cost:** 260 ms with bloom on, and
  327 ms more with bloom off. On this table they also make the file larger
  (38.4 MB with dictionaries vs 33.6 MB without, both with bloom off).
- **Bloom filters** cost 55 ms when dictionaries are on (the row hashes are needed
  for the dictionary decision anyway) and 123 ms when they are off. They are 10 MB
  of the 48 MB file: a filter sized at fpp 0.01 for about 48k distinct values,
  for every column in every one of the 4 row groups.
- **With both off, rugo is 1.28x polars on one thread** (358 ms vs 279 ms) and
  writes a smaller file (33.6 MB vs 36.3 MB). zstd's cost is about the same in both:
  225 ms in rugo vs 191 ms in polars. Part of that difference is the level: rugo
  uses 4 and polars defaults to 3. polars at level 4 takes 291–308 ms and writes
  35.9 MB.

### By column type, one thread

| type (columns) | rugo default | rugo bloom off | rugo dict off | rugo both off | polars 1t |
|---|---:|---:|---:|---:|---:|
| INT64 (17) | 156 ms / 17.1 MB | 134 / 10.7 | 158 / 17.2 | 103 / 10.8 | 65 / 10.9 |
| FLOAT64 (17) | 149 / 16.0 | 148 / 16.0 | 107 / 12.7 | 107 / 12.7 | 75 / 13.0 |
| VARCHAR (16) | 414 / 15.1 | 377 / 11.7 | 200 / 13.4 | 138 / 10.0 | 129 / 12.5 |

- **INT64:** the dictionary gate almost never adopts a dictionary. Only `c000`,
  with 1,000 distinct values, is cheap enough. But computing the decision costs
  31 ms (103 → 134 ms). The bloom filters add 55 ms and **6.4 MB, which grows the
  file by 60%.**
- **FLOAT64:** dictionaries are adopted, cost 42 ms, and **make the file 26%
  larger** (16.0 MB vs 12.7 MB).
- **VARCHAR:** dictionaries are adopted, cost 214–239 ms (bloom on vs off), and **make the file 17%
  larger** (11.7 MB vs 10.0 MB).

Why the floats and strings get adopted: each 65,536-row chunk has about 48k
distinct values. The gate compares *uncompressed* bytes:
`dict_page + 16-bit codes <= 1.05 x PLAIN`. For a double that is 386 KB + 131 KB
against 550 KB, so the dictionary wins on paper. After zstd it loses. PLAIN floats
and short strings compress well, but random 16-bit codes do not. The comment above
`DICT_BYTE_TOLERANCE` in `_parquet_writer.hpp` records that the uncompressed-only
gate was a ruling ("Ruled (2026-09-16)"). This table is a case where it costs both
size and time.

## 3. Threading

These are best of 5, with "CPU" being process CPU time for the same write:

| format | rugo wall | rugo CPU | polars 18t wall | polars 18t CPU | polars 1t | pyarrow 1t | duckdb 1t |
|---|---:|---:|---:|---:|---:|---:|---:|
| Parquet | 740 | 750 | 24.5 | 365 | 279 | 346 | 350 |
| CSV | 222 | 223 | 10.9 | 136 | 106 | 207 | 340 |
| JSONL | 68 | **440** | 17.2 | 220 | 180 | n/a | 398 |

- **polars gets 11.4x (Parquet), 9.7x (CSV) and 10.5x (JSONL) from its 18 threads.**
  That is the larger factor in every format.
- **rugo's JSONL writer is not faster per core than polars, despite its wall
  time.** It renders on 8 pool threads (`kJsonlMaxThreads = 8`, with 16,384-row
  partitions) and burns 440 ms of CPU, 2.4x what polars needs on one thread. Its
  wall time looks close only because of the threads.
  - Its scaling is 440 ms CPU to 68 ms wall on 8 threads, about 6.5x. That is the
    reference point for what a parallel rugo writer gets on this machine.
  - CPU per thread is inflated on the efficiency cores (see the PEcores memory note).
- pyarrow's Parquet and CSV writers are single-threaded whatever `set_cpu_count`
  says: 346 ms vs 346 ms, and 207 ms vs 209 ms. duckdb's writers get 1.5x
  (Parquet) and 1.5x (CSV) from all its threads.

### Text writers by column type, one thread (JSONL: CPU time)

| type | rugo CSV | polars CSV 1t | rugo JSONL (CPU) | polars JSONL 1t |
|---|---:|---:|---:|---:|
| INT64 (17) | 23.4 | 21.2 | 61 | 45 |
| VARCHAR (16) | 32.3 | 34.3 | 93 | 53 |
| FLOAT64 (17) | **150** | **46** | **237** | **74** |

**rugo's CSV writer is at parity with polars on ints and strings; the entire CSV
gap is the 17 float columns.** The output is byte-identical (82,426,105 bytes from
both), so both produce the same shortest round-trip text, and the gap is pure
formatter cost. JSONL shows the same pattern, plus the 8-thread CPU inflation.

## 4. Profiles: where the time goes

### Parquet, defaults (765 ms/iter, 16,267 samples)

| incl. | where |
|---:|---|
| 50% | `build_dict_column` (sorting, encoding and compressing the dictionary and its codes) |
| **26%** | `std::__introsort` inside `build_dict_column`: **sorting the dictionary** (`_parquet_writer.hpp:1824`, an indirect `perm` sort with a `str_lt` / memcmp comparator for strings) |
| 24% | zstd (`ZSTD_compressBlock_doubleFast` alone is 17% self) |
| **11.4% + 1.7%** | `bloom_ndv`: copies the 65k-entry hash vector **by value**, then `std::sort`s it to get an *exact* NDV. This is libc++'s out-of-line `__sort<uint64_t>`, called from `_parquet_writer.hpp:2446`. |
| 9% | `encode_values` (PLAIN) |
| 8% | building the dictionary hash tables (`build_string_dict` 4.6%, `build_numeric_dict<double>` 4.0%) |
| 5.3% | `compute_stats` (memcmp for string min/max) |
| 2.6% | `hash_column_rows` (XXH64, shared by bloom and the dictionary decision) |
| 3.0% | `encode_dict_indices` |

The sort exists to set `is_sorted` on the dictionary page, as
`SORTED_DICTIONARY_DESIGN.md` describes. It sorts about 48k strings per chunk,
for 16 string columns x 4 row groups.

### Parquet, `bloom_filters=False, dictionary=False` (358 ms/iter)

| incl. | where |
|---:|---|
| 61% | zstd level 4 (`doubleFast` is 46% self) |
| 22% | `encode_values`: byte-at-a-time `vector::push_back` (`put_u32_le` 2.5%, `vector<char>::insert` 5%) |
| 11% | `compute_stats`, mostly memcmp for string min/max |
| ~1% | the per-chunk zstd context reset, Python and staging |

Every zstd page also keeps a second, uncompressed copy (`pb.plain_bytes`). The
"stored raw if not smaller" floor check needs it, and it doubles the output-side
memcpy.

### CSV (210 ms/iter, 8,789 samples)

| incl. | where |
|---:|---|
| **74%** | `ec_float`: float formatting, for 17 of the 50 columns |
| 45% | ↳ ryu `d2s_buffered_n` (`d2d` is 34%, `to_chars` 10%), about 30 ns per double |
| 24% | ↳ `fmt_shortest_digits`, plus `fmt_shortest` reparsing ryu's `D.DDDE±XX` text back into digits and an exponent. 18% of all samples are libc `memcpy`/`memmove` on 1–17 byte runs, from `value_format.hpp:192–214` |
| 9.4% | `csv_field` (strings) |
| 9.0% | `fmt_int64` |

The float path writes scientific text, parses it back, reshapes it and appends
it: three passes over every value. polars spends about 13.5 ns per float **all in**
(46 ms for 3.4M floats, including the CSV framing). That is less than ryu's core
alone here (about 30 ns), so polars uses a cheaper shortest round-trip formatter.

### JSONL (70 ms/iter, 31,905 samples on 8 workers plus the main thread)

| self | where |
|---:|---|
| ~56% | float formatting: `d2s_buffered_n` 33.8%, the `fmt_shortest_digits` memcpys 13.7%, `ej_float` 5.1%, `fmt_shortest_digits` 3.0% |
| 12.8% + 3.5% | `jsonl_render_rows`, plus appending the key prefixes |
| 6.3% | `json_string` |
| 5.9% + 2.5% | `fmt_int64` / itoa |
| about 2% | the main thread: concatenating the 8 chunks into `bytes` |

All 8 workers have balanced loads (3,898 to 4,380 samples each).

## 5. Fix proposals, ranked by expected wall-clock gain

Two kinds of estimate appear below. "Measured" means the saving was observed by
toggling an existing knob. "Estimated" is derived from profile shares or from the
JSONL writer's 6.5x scaling. Rulings needed are marked ⚖.

1. **⚖ Encode Parquet column chunks in parallel.** The loop over columns in
   `encode_row_group` handles 50 cols x 4 row groups = 200 independent chunks
   (stats, hashing, dictionary, encode, zstd). Only placing them in the file is
   serial.
   - *Expected:* about 6.5x on wall time, judged by the JSONL pool on this machine
     (polars gets 11.4x on 18 threads). That takes 740 ms to about 115 ms at the
     defaults, and 358 ms to about 55 ms with bloom and dictionary off. This is
     the single largest lever.
   - *Note:* `PARQUET_WRITER_DESIGN.md` records the writer as deliberately
     single-threaded, so this needs a ruling. It would reuse the vendored
     `BS::thread_pool` that the JSONL writer already uses.

2. **⚖ Change the dictionary gate for high-NDV chunks.** On this table the gate
   adopts dictionaries that lose after zstd, costing time and size together.
   - *Measured ceiling for this table:* −42 ms and −3.3 MB on floats, −214 to −239 ms
     and −1.7 MB on strings. The full table goes from 740 to about 481 ms and from
     48.2 to 43.4 MB (the `dictionary=False` row).
   - *Options:*
     - (a) Reconsider the 2026-09-16 uncompressed-only ruling, for example by
       zstd-compressing a sample of both encodings when NDV/n is above about 0.5.
     - (b) Refuse a dictionary when the code width is 16 bits or more and NDV/n is
       above a threshold, since random codes do not compress.
     - (c) Leave the gate as it is and accept the cost.
   - The trade-off is reader-side: a sorted dictionary allows code-range predicates
     and the dict-skip probe.

3. **⚖ Make float-to-text cheaper (CSV and JSONL).** This is the entire per-core CSV
   gap and most of JSONL's.
   - *Step a, no new dependency:* call ryu's `d2d` (the decimal mantissa and
     exponent) and write digits straight into the output buffer. That skips the
     scientific text, `fmt_shortest`'s reparse and the small out-of-line memcpys.
     *Estimated:* −24 to −29% of CSV CPU (the `fmt_shortest_digits` + `ec_float`
     share), taking CSV from 220 to about 160 ms on one thread, and JSONL CPU from
     440 to about 330 ms. The same values must come out, which the byte-identical
     comparison against polars can check.
   - *Step b, needs vendoring agreement:* a faster shortest round-trip algorithm
     than ryu. *Estimated:* floats reach polars' parity (46 ms for 17 columns),
     taking CSV to about 105 ms on one thread, since ints and strings are already
     at parity.

4. **⚖ Parallelise the CSV writer** using the same row partitioning as `jsonl_write`.
   That code already exists in `_text_render.hpp`; only the header row and the
   `for_excel` checks stay serial.
   - *Expected:* about 6.5x, so CSV goes from 220 to about 35 ms. With fix 3 as
     well, about 16–25 ms, against polars' 10.9 ms.
   - *Also:* raise `kJsonlMaxThreads` (8) to the core count. *Estimated:* JSONL
     goes from 68 to about 40 ms on this 18-core box. It gains nothing on Cloud Run
     instances with 8 or fewer vCPU.

5. **Sort the dictionary more cheaply,** if dictionaries stay on for these chunks.
   The indirect `std::sort` of `perm` with a memcmp comparator is 26% of default
   Parquet CPU, about 200 ms.
   - *Option:* sort `(big-endian 8-byte prefix, code)` pairs, using an integer
     compare or a radix sort, and memcmp only on prefix ties. For `text-NNNNN`
     strings the prefix decides almost every compare.
   - *Estimated:* −100 to −150 ms. Not measured. Most of it is moot if fix 2
     declines these dictionaries.

6. **⚖ Size the bloom filter from an estimated NDV instead of an exact one.**
   `bloom_ndv` copies and sorts 65k hashes per chunk (13% of default CPU) to get an
   exact count. The KMV sketch that is already used when bloom is off
   (`dict_estimated_ndv`, 2.4%) could size the filter, with a margin.
   - *Measured ceiling:* −55 ms, which is all of bloom's cost with dictionaries on.
   - *Ruling needed:* the exact NDV also feeds the footer's `distinct_count`
     statistic. Making that an estimate changes a written contract.
   - *Separately:* blooms are 10 MB of the 48 MB file. Whether they should be on by
     default is policy, not a speed bug. The read side uses them (see the
     bloom_filter_read_pruning memory note).

7. **Fix the bare Parquet per-core overheads.** Bare rugo takes 358 ms against
   polars' 279 ms on one thread.
   - **Byte-wise `push_back`** in the PLAIN and header encoding: write into a
     pre-sized buffer instead. *Estimated:* −20 to −40 ms of the 79 ms
     `encode_values` share.
   - **The second uncompressed copy of every page,** made for the size-floor check.
   - **zstd level 4 vs polars' 3:** measured on polars at about +15 ms for −0.45 MB.
     This is policy (`zstd_level_for`) and needs a ruling to change.

If fixes 1, 2 and 6 all land, Parquet at the defaults is estimated at about
740 − 260 − 55 ≈ 425 ms on one thread, and about 65 ms with parallel encoding.
That is still about 2.7x polars' 24.5 ms. Closing the rest needs fix 7 and full
core use. CSV with fixes 3 and 4 lands within about 2x of polars. JSONL with fix 3
and a wider pool lands around 1.5–2x.

## 6. What was built (2026-10-16)

### Result

These figures use the benchmark table on the same machine. Each is the best of 5
writes, over 5 alternating rounds, with the median in brackets. "Before" is the
pre-change tree build; "after" is the final code.

| format | rugo before | rugo after | speed-up | polars (18t) | polars 1t | pyarrow | duckdb |
|---|---:|---:|---:|---:|---:|---:|---:|
| Parquet (zstd) | 739 (754) | **84 (87)** | 8.8x | 23.5 | 280 | 348 | 223 |
| CSV | 214 (222) | **36 (37)** | 6.0x | 10.5 | 106 | 209 | 214 |
| JSONL | 65 (67) | **42 (44)** | 1.6x | 15.9 | 179 | n/a | 259 |

- **Against pyarrow and duckdb,** rugo is now faster in every format.
- **Against polars,** the gap went from 31x to 3.6x (Parquet), 20x to 3.4x (CSV)
  and 4x to 2.6x (JSONL).
- **Output:** CSV and JSONL bytes are unchanged. Parquet output is byte-identical
  to the pre-change writer: the kept parts change speed only.
- **Arch:** this is ARM (M-series) only. Per the arch-aware ruling, the x86 A/B
  is still owed.

### Kept (passed the keep rule)

The keep rule was written before measuring, in the shared notes as
`writer_speed_keep_rule.md`. Each part was compared as FULL vs FULL-minus-part,
over 12 alternating rounds, on 13 shapes. A part is kept only if some shape it
touches reaches a median B/A ≤ 0.98 with ≥ 10/12 paired wins, and no shape it
touches is above 1.00.

| part | where | median wall B/A, FULL vs without it |
|---|---|---|
| Parallel Parquet column-chunk encode | `encode_row_groups` / `encode_column_chunk` in `_parquet_writer.hpp`: every chunk of a block is a task on the shared pool; placement stays serial, so the bytes are unchanged | 0.14–0.22 on every Parquet shape |
| Shared writer pool sized to the core count (was 8 for JSONL) | `rugo/src/_writer_pool.hpp`, used by both writers | 0.71–0.88 on large shapes; 1.00 on 5k rows |
| Parallel CSV render | `csv_write` returns per-worker chunks, the same partitioning as JSONL; `_csv_writer.pxi` concatenates them into one `bytes` | 0.20–0.23 (csv_wide, csv_float); 1.00 on 5k rows, which stays serial |
| Direct float text | `fmt_double` / `fmt_float` lay out ryu's integer decimal directly (`fmt_decimal_shortest`), without printing scientific text and parsing it back | 0.72–0.85 on all six CSV/JSONL shapes |
| Presized PLAIN encode | `encode_fixed_plain`; BYTE_ARRAY sized once | 0.91–0.98 |
| Exact bloom NDV via a hash set | `bloom_ndv`: no copy, no sort; still exact, so `distinct_count` is unchanged | 0.90–0.98 |

### Deleted (failed the keep rule)

- **Prefix-key dictionary sort (§5 fix 5).** It helped only pq_dict (0.972) and
  was slower on pq_url (1.025) and pq_wide (1.018). URLs share their first 8 bytes,
  so every key ties and falls through to the full compare.
- **zstd-aware dictionary gate (§5 fix 2, option a).**
  - *v1* decided before the dictionary build, using a sampled zstd ratio. It was a
    large win on pq_str (0.70), pq_wide (0.80) and pq_float (0.83), and made the
    files 10% smaller. It was vetoed by pq_small at 1.111: on a 5k-row chunk the
    sample is the whole chunk, compressed even when the byte budget would refuse
    the build anyway.
  - *v2* decided after a successful build. It kept pq_str (0.80) and pq_wide (0.87)
    but was vetoed by pq_float (1.075), because the float build is then paid for
    before the refusal, and by pq_url and pq_int (1.016).
  - Both versions were deleted. The uncompressed-only gate (the 2026-09-16 ruling)
    stands unchanged. The size win measured in §2 (48.2 → 43.4 MB on this table)
    is therefore not in the tree.

### Not built

- **A faster shortest round-trip algorithm than ryu (§5 fix 3b).** It needs a
  vendoring decision. The remaining float cost is ryu's own `d2d`.
- **Bloom sizing from an estimate (§5 fix 6).** Not needed: the hash-set count keeps
  the exact NDV, so the `distinct_count` contract is unchanged.
- **Dropping the second, uncompressed copy of each page,** and the zstd level
  (§5 fix 7). Neither was attempted. The level is policy.

### Vendored-code change

`third_party/ulfjack/ryu/d2s.c` and `f2s.c` each gained one exported function,
`d2s_decimal` / `f2s_decimal`, declared in `ryu.h` and marked "Opteryx addition
(2026-10-16), not upstream ryu". Each returns the decimal mantissa and exponent
that `d2s_buffered_n` / `f2s_buffered_n` would print. They mirror the upstream
functions' bodies and stop before `to_chars`.

### Verification

- **Float text:** byte-identical between the old and new paths on 4M random-bit
  doubles and 4M random-bit floats. A new test, `tests/rugo/test_float_text_direct.py`,
  pins the output against CPython `repr` (float64) and against the shortest
  round-trip text (float32), including every layout boundary.
- **Parquet bytes:** identical with each of the parallel encode, NDV set and
  presized encode switched off. Checked on 8 option sets (compression, page
  splitting, a single row group, bloom off, dictionary off, block size 1, the
  storage profile), each on the wide table and on a 10%-null table.
- **New tests** in `tests/rugo/test_parquet_writer_dictionary.py` pin the sorted
  dictionary order on prefix ties, high bytes and the int64 extremes.
- **Suites:** `make q`, `make slt`, `make rt` (2,875 passed), `make dt` (3,596) and
  `make st` all pass. `make -C skene bench` builds; its include path gained
  `third_party/bshoshany`.

### Full ClickBench rewrite (the opteryx-parquet entry's load step)

- **Setup:** `ClickBench-167/opteryx-parquet/convert.py` with the entry's own
  arguments (zstd, 64k-row row groups, blocks of 4) on the 100-file, 14 GB `hits`
  set, on this Mac (18 cores). The budget is `-m 40` GiB, which allowed 9
  concurrent workers.
- **Trees:** two clean ones built from the same source snapshot: the pre-change
  writer, and the current one.
- **Order:** ABBA, one full rewrite per cell. Each rewrite reads every file
  through Opteryx, sorts it by the primary key, writes it, and verifies it.

| run | base | new |
|---|---:|---:|
| 1 | 91.5 s | 59.4 s |
| 2 | 87.2 s | 58.8 s |

- **Result:** **89 s → 59 s, 0.66x (1.5x faster).** The output is identical:
  9,946,412,822 bytes and 99,997,497 rows in both.
- **Smaller gain than the single-file benchmark:** the rewrite already runs 9
  files at once, so the writer's internal threads compete for the same cores,
  and reading, sorting and verifying are unchanged.
- **For reference:** the published c6a.4xlarge load was 292 s on 0.9.167, with 16
  cores and 5 concurrent workers under a 20.8 GiB budget. That figure predates
  these changes and has not been re-measured.

  - `base` is the same tree with the pre-change versions of the touched files
    restored. Those come from the snapshot taken before the first edit; the ryu
    additions are stripped and `_writer_pool.hpp` is removed.
  - Both were built with `make compile`.
- **Data:** `wide.csv` is regenerated with the same seed and byte-identical in
  size (82,626,106 B). The other shapes are generated the same way as on ARM.
- **Method:** fresh process per cell, best of 5, arm order alternated, 12 rounds,
  13 shapes. Output bytes were identical between the arms for every shape.

- **Parquet: 4–5x faster on x86** (pq_wide 2,310 → 572 ms). On ARM it was about
  9x. The box has 6 cores to the Mac's 18, and its single-thread base is 3x slower.
- **CSV: 2–3x faster** (csv_wide 0.48). The parallel render is capped by 6 cores.
  csv_small is single-threaded, so it isolates the float change: 0.903.
- **JSONL: float-heavy and single-thread shapes are faster** (0.90–0.96).
  jsonl_wide is the one shape where the metrics disagree, so it was examined
  separately:
  - **Best of 5** puts it at **1.116 (0/12)**.
  - **Within-process median** puts it at 0.986 (7/12). A single process spreads
    298–371 ms across its 5 writes of 159 MB, so best of 5 records the luckiest
    run, not the code.
  - **3-way A/B** (base / new / new with only the float change reverted, rebuilt
    on the box): by median, new / no-float = 0.985 and new / base = 0.992.
  - **`perf stat`, mean of 20 writes, 4 alternating rounds:** base 371–375 ms/iter,
    new 322–365, no-float 322–360. Both new builds fall into the same two bands
    (~322 or ~360 ms) regardless of build.
  - **Hardware counters:** the float change removes 9.5% of instructions
    (82.6B vs 91.2B) at unchanged cycles (94–102B in both). IPC is 0.82–0.91: on
    the i5 this shape is bound by memory traffic, not formatting.

  So on x86 the float change is cycle-neutral for jsonl_wide and a win where
  formatting dominates. No x86 regression is established. The 1.116 is an
  artefact of using best of 5 on a bandwidth-bound shape.
- **Profile note:** on Linux, rugo's text writers resolve `fmt_double` to
  draken_native's copy through ELF symbol interposition. `perf` attributes the
  float samples to `draken_native`, and the change has to be in both `.so` files
  to take effect. Both builds were rebuilt.

## Found in passing (not in scope; reported, not touched)

- `draken.draken_native.vector_float64_from_sequence` turns `-0.0` into `0.0`, so
  a signed zero is lost before any writer sees it. I did not touch it.
- `jsonl_write` called `f.get()` on each render future in turn. A failing worker
  could therefore unwind `cols` / `chunks` while the others were still using them.
  Because I was rewriting that function to share the pool with CSV, it now waits on
  every future before surfacing the first failure, the same as the new CSV path.
  This is a change outside the agreed list, so I'm calling it out explicitly.

- `rugo/__init__.py:13-16` does `try: import pyarrow / except ImportError: pass`,
  described as a "load-order bug" workaround. That breaks CLAUDE.md §4 (PyArrow
  banned from `rugo/`) and §9 (no try/except as control flow). It loads
  libarrow, libparquet and numpy into every rugo process where pyarrow is
  installed: 53 ms of import time measured with `-X importtime`. It does not affect
  the write timings above.
- `rugo.parquet.read_metadata` does not expose per-chunk encodings, so I could not
  read which columns were dictionary-encoded straight from the output. That was
  inferred above from the per-type size deltas instead.
